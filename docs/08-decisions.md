# 08. Решения (ADR) и открытые вопросы

Формат: решение — почему — последствия. Статус у всех «принято» на 2026-11-25, если не указано иное.

## ADR-001. LLM через OpenAI-совместимый API, по умолчанию OpenRouter
- **Почему:** владелец выбрал OpenRouter (выбор моделей, баланс $1–2). Тот же протокол поддерживают внутренние шлюзы, vLLM и Ollama, а это ключ к встраиванию в банк.
- **Последствия:** один клиент `openai` SDK; особенности OpenRouter (`provider.require_parameters`, `usage.cost`) включаются только для openrouter.ai. `google-genai` не используем.

## ADR-002. Формат отчёта = формат входа, плюс JSON всегда
- **Почему:** решение владельца; ТЗ требует «файл» без формата. JSON нужен для интеграции и eval.
- **Последствия:** PDF-рендер обязателен в MVP (риск со шрифтом, нужен спайк). TXT на входе даёт MD на выходе. DOCX — P1.

## ADR-003. Вердикт и счётчики считает код
- **Почему:** ТЗ требует ответа «можно ли начинать»; решение модели не воспроизводимо и не объяснимо.
- **Последствия:** пороги в `thresholds.yaml`, правило печатается в отчёте.

## ADR-004. Находка без проверенной цитаты не попадает в отчёт
- **Почему:** ТЗ: «каждое нарушение ссылается на конкретное место». Это главная защита от галлюцинаций.
- **Последствия:** часть верных находок может отсеяться; они остаются в `debug.dropped_findings`, их долю видно в eval.

## ADR-005. Выделение требований по структуре, а не по глаголам
- **Почему:** в документе из ТЗ почти нет «должен»; требования заданы пунктами `Ф-N`, разделами и строками таблиц.
- **Последствия:** кандидаты кодом (нумерация, разделы «Требования…», таблицы), затем LLM отсеивает и делит составные.

## ADR-006. Противоречия: кандидаты кодом, подтверждение моделью
- **Почему:** попарная проверка O(n²) вызовов не укладывается в бюджет.
- **Последствия:** кандидаты по общим сущностям, числам с единицами, датам и зонам, кодам HTTP; модель видит только кандидатов и соседний контекст.

## ADR-007. Сервер — опциональное дополнение, UI без сборщика
- **Почему:** жюри нужен только CLI; лёгкость установки важнее. Банку нужна OpenAPI-спецификация.
- **Последствия:** `pip install reqcheck[server]` ставит FastAPI и uvicorn; UI — три статических файла, без npm.

## ADR-008. Кэш вместо `temperature=0` как основа воспроизводимости
- **Почему:** многие модели на OpenRouter не принимают `temperature`.
- **Последствия:** ключ кэша включает модель, промпт, схему и версию промпта; повторный прогон воспроизводит отчёт побайтно.

## ADR-009. Цитата показывается в исходном документе (P1)
- **Почему:** находке доверяют больше, когда её видно в оригинале; аналитику удобнее править свой документ с пометками, чем сверять отчёт вручную.
- **Решение:** координаты цитаты сохраняются на этапе `verify` (он и так ищет цитату). Первым делаем исходный PDF с пометками, затем фрагмент в UI, затем ссылки в отчёте.
- **Последствия:** `Anchor` получает поле `rects`; два новых эндпоинта API; для сканов без текстового слоя фрагмента нет до OCR.

## ADR-010. PDF-фикстуры строим через pymupdf.Story, а не reportlab
- **Почему:** `pymupdf` уже в зависимостях, шрифты с кириллицей уже лежат в `reqcheck/render/fonts`; reportlab ради трёх файлов — лишняя dev-зависимость (удалена из `pyproject.toml`). Фикстуры заодно сквозной тест PDF-входа (`pymupdf4llm`).
- **Последствия:** `tests/fixtures/make_fixtures.py` сверяет цитаты `expected.yaml` с текстом при генерации, а `tests/test_eval.py` — с ингестом готовых PDF. Тексты общие (вымышленный магазин), подгонки под документ организаторов нет.
- **Известные особенности (найдены на фикстурах):** (1) ~~при извлечении текста латинская «A» превращалась в «Ă»~~ — **исправлено 2026-11-26.** Причина: у Golos Text в GSUB на латинице по умолчанию (`latn/dflt`) есть `locl`, который заменяет «A» на глиф «A.1» (gid 258). Вёрстка MuPDF (HarfBuzz) ставит этот глиф, а ToUnicode MuPDF строит по cmap, где у «A.1» записи нет; при извлечении MuPDF подставляет номер глифа как символ: 0x0102 → «Ă» (а «Ă» → «Ą»). Подмножества шрифтов ни при чём. Исправление: dev-скрипт `scripts/font_alternates.py` (fontTools только в dev-группе) строит таблицу «альтернатива GSUB → текст» `reqcheck/render/fonts/alternates.json`, а `reqcheck/render/tounicode.py` после рендера дописывает недостающие коды в ToUnicode (PDF-отчёт и фикстуры). Шрифты не меняются. Проверено извлечением текста из сгенерированного PDF (`tests/test_render.py`). (2) `pymupdf4llm` склеивает слово с дефисом на переносе строки («интернет-магазина» → «интернетмагазина»): для цитат это терпимо (нечёткий поиск), но в заголовках видно.

## ADR-011. Снижение шума: потолки серьёзности, лимиты набора, этап confirm
- **Почему:** на `clean.pdf` конвейер давал 6–11 находок, среди них выдуманные blocker-противоречия; каждое такое переворачивает вердикт «можно ли начинать разработку».
- **Решение:** (1) `max_severity` в `thresholds.yaml`: модель повышает серьёзность выше умолчания, но не выше потолка категории; (2) `findings_filter.max_set_per_category` (и `drop_unclear_up_to`; порог major пришлось вернуть к minor: сильная модель оформляла настоящие дефекты как «неясно», а на вердикт такие находки не влияют); (3) промпты `check_each` v3 и `check_set` v2 с перечнем того, что не считать нарушением; (4) этап `confirm`: один короткий вызов проверяет заявленные противоречия: `conflict` остаётся, `compatible` уходит в debug, `other_issue` («не противоречие, но проблема есть») превращается в находку `incorrect`; при ошибке вызова находки остаются.
- **Последствия:** ложные на clean: luna 6 → 5 (серьёзных 4 → 2), deepseek 11 → 8 (серьёзных 10 → 8), числа в [таблице](../eval/results/2026-11-26-comparison.md); +1 вызов на документ с противоречиями. Побочный эффект: у luna recall на defects 91 % → 82 % (один дефект сменил категорию) и на contradictions 100 % → 75 % (одно противоречие стало «некорректностью»), в пределах разброса. Отфильтрованное видно в `debug.suppressed_findings`. Исправить подтверждающую модель на пропуск настоящих противоречий можно только сменой промпта: она может ошибаться (см. фикстуру с адресами).

## ADR-012. Eval: dev/holdout, разметка организаторов, повторы и решающий прогон
- **Почему:** на трёх фикстурах конвейер настраивали и мерили на одних и тех же данных; нужна честная оценка, разброс и ответ на вопрос «конвейер или один промпт».
- **Решение:** (1) корпус 14 документов (8 dev, 6 holdout, MD и PDF, все 14 категорий); для `missing_topic`/`traceability` режим сопоставления по разделу (`sections`, «*» — где угодно), находке всё равно нужен проверенный кодом якорь — заголовок раздела (`locate_heading`); (2) документ организаторов размечен в `eval/labels/organizers.yaml` (только eval, только holdout, **не проверено владельцем**), в config/промпты не переносится — это проверяет тест на утечку; (3) `--repeat N`: соль кэша только для повторов eval, таблица со средним; (4) `--hybrid-at N` считает маршрутизацию по размеру из тех же прогонов без новых вызовов; (5) оценка `--dry-run` получила множители из `config/thresholds.yaml` (`estimate`): на прогоне 2026-11-27 факт превысил оценку в 2,5× (конвейер) и 3,5× (baseline, разброс по документам 0,5–9×).
- **Результат решающего прогона ([таблица](../eval/results/2026-11-27-gate.md), deepseek, 1 годный повтор из 3):** конвейер — dev 94 %, holdout 59 %, ложных на чистых 10 / 7, $0,072; baseline — dev 84 %, holdout 64 %, ложных 2 / 30, $0,045, обрезан на 2 документах; hybrid ≤40 — holdout 50 %, ≤60 — 60 %. Baseline выиграл на 3 из 4 больших holdout-документов, конвейер — на документе организаторов (58 % против 47 %) и там, где baseline обрезан.
- **Вывод:** данные **противоречат плану** (конвейер не выигрывает на больших документах, маршрутизация по размеру ничего не даёт). По правилу задачи дальнейшая работа в этой области (упрощение конвейера, маршрутизация, этап 2 — снижение шума) **остановлена до решения владельца**. Повторы 2–3 сорваны лимитом, разброс не измерен: разница 59/64 % может быть шумом.
- **Разброс (3 повтора на holdout, владелец выбрал «сначала измерить», [таблица](../eval/results/2026-11-27-gate.md)):** конвейер — recall holdout 50 % (43–59 %), ложных на чистом 8,3 (7–11); baseline — 57 % (33–76 %), ложных 52 (30–72), обрезан в 4 из 18 прогонов. Разница по recall — в пределах разброса; по шуму конвейер стабильно лучше в 6 раз. Провалы конвейера на документе организаторов (2/19 и 1/19 против 11/19) — из-за вырожденного ответа `check_set` (одна пустая находка без цитат; 5 из 12 вызовов deepseek), который код отбрасывает, а отчёт остаётся «полным». Это ошибка надёжности, а не подхода.
- **Исправлено 2026-11-27 (решение владельца: «починить, без перезапуска»):** `stages/empty.py` распознаёт вырожденный ответ (все находки без цитат и пояснения; пустой список — нормальный ответ) в `check_set` и baseline, повторяет вызов один раз с поправкой `prompts/empty_retry.md` (другой ключ кэша — повторный прогон воспроизводит обе попытки), а повторная пустота — ошибка этапа, отчёт «неполный». По кэшу: так выглядят 11 из 42 ответов `check_set` у deepseek и ни одного у luna, haiku, sonnet. Платный перезапуск не делали: эффект на recall не измерен.
- **Этап 2 (снижение шума) не делали.** Причины: (1) по шуму на чистых документах конвейер уже в 6 раз лучше baseline (8 против 52), а главный провал оказался ошибкой надёжности, а не шумом; (2) честное «до/после» требует платных повторов, а из согласованных $0,40 осталось ≈ $0,06. Дешёвый путь на будущее: фильтры, которые работают после LLM (verify, фильтр шума), можно мерить бесплатно — eval с теми же `--repeat` берёт ответы модели из кэша.
- **Варианты для владельца:** (а) ещё 1–2 повтора deepseek на holdout (≈ $0,05 за повтор по новой оценке) — измерить разброс до любых решений; (б) починить у конвейера потерю находок check_set с пустой цитатой и пропуски дублей/терминологии, затем перемерить; (в) у baseline поднять `max_tokens` и фильтровать шум кодом, рассмотреть baseline + этапы verify/confirm как «облегчённый» режим; (г) оставить конвейер по умолчанию (он лучше на документе организаторов и стабильнее по шуму на чистых), baseline — как режим сравнения в UI.

## ADR-013. DOCX через Markdown: один разбор и одна проверка цитат
- **Почему:** в банке требования пишут в Word; отдельный разбор DOCX дал бы второй набор якорей и второй путь проверки цитат.
- **Решение:** опция `reqcheck[docx]` (python-docx 1.2). Вход: `ingest/docx.py` переводит документ в Markdown (заголовки по стилям «Heading N»/«Заголовок N»/«Title», списки по стилю или `numPr`, таблицы — строками) и отдаёт его общему `MarkdownParser`. Выход: `render/docx.py` строит DOCX из нашего же Markdown-отчёта, поэтому цитаты в DOCX те же, что проверил код (это проверяет тест). Формат отчёта по умолчанию = формат входа (ADR-002): DOCX → DOCX.
- **Последствия:** у якорей DOCX нет номеров строк — ссылкой служит путь раздела; автонумерация Word (1., 1.1) в текст абзаца не входит и теряется, номера, набранные текстом («Ф-1.»), сохраняются. Без установленной опции — понятная ошибка с командой установки. Фрагмент оригинала в UI для DOCX — абзацы, как у Markdown.

## ADR-014. OCR сканов — флаг `--ocr` и Tesseract, без pip-опции
- **Почему:** скан без текстового слоя раньше давал только ошибку (Q3). Распознавание уже есть в установленных PyMuPDF 2.1 / pymupdf4llm 2.1 (`to_markdown(use_ocr=..., ocr_function=..., ocr_language=..., ocr_dpi=...)`), нужен только бинарник Tesseract с данными языков — pip-пакет для этого не нужен, поэтому отдельной опции `reqcheck[ocr]` нет.
- **Решение:** `--ocr` (CLI) и `Options(ocr=True)` (библиотека) включают OCR только для страниц без текста; движок задаём явно (`pymupdf4llm.ocr.tesseract_api.exec_ocr`), потому что автовыбор pymupdf4llm молча берёт RapidOCR, если он установлен. Язык и DPI — `config/ingest.yaml` (`ocr`, по умолчанию `rus+eng`, 300). До импорта движка код проверяет `pymupdf.get_tessdata()` и наличие `<язык>.traineddata`: нет Tesseract или языка — ошибка с командой установки (код 3), а не пустой отчёт.
- **Последствия:** у распознанных страниц нет текстового слоя в исходном PDF, поэтому координат цитат (rects), пометок и PNG-фрагментов для них нет — находки и цитаты есть. Проверено тестами с подменённым движком и вручную на машине без Tesseract (сообщения об ошибке); **распознавание на настоящем Tesseract не проверено** — его нет в окружении разработки. В Docker-образе Tesseract с `rus` ставится.

## ADR-015. Независимое ревью итогового отчёта и правило тест-дизайна
- **Почему:** 2026-11-27 итоговый отчёт (`docs/after`, Sonnet, агент `0b0b506`) проверили три независимых ревьюера (Claude Opus 5.5 по подписке, без OpenRouter): слепое ревью документа, проверка каждой находки, сверка с ТЗ.
- **Что нашли:** все цитаты настоящие, счётчики сходятся. Но из трёх blocker обоснован один (F-014); F-011 ложная (границы порога есть в Ф-1 и `amount`), F-015 завышена и дублирует F-013; F-008, F-009 ложные. Пропущено противоречие критерия приёмки и Ф-2 (месяц по дате совершения против «февральского счётчика»), 200 с `ERROR` против 400, «чтение порога» без метода. По `eval/labels/organizers.yaml` — 6 из 19. Отчёт говорил «можно начинать тест-дизайн», хотя F-014 прямо мешает написать тест.
- **Решение (бесплатное, без перепрогона):** правило тестирования в `config/thresholds.yaml` получило `caution_testing_if_blockers_at_least: 1` — при blocker вердикт по тестам «с оговорками» и перечень требований, ожидаемый результат для которых не определён (`can_start_testing` остаётся `true`, как «с оговорками» у разработки). Шаблон Markdown: вердикт наверху, легенда «неясно», цитаты и предложения отдельными строками. `.md`/`.pdf` в `docs/after` перерисованы из JSON без вызовов модели; содержание и вердикт отчёта не менялись.
- **Не сделано (нужен платный перепрогон и согласие владельца):** запрет в промптах находок и допущений, противоречащих тексту документа (F-011, вопрос 1); проверка критериев приёмки против функциональных требований; перегенерация отчёта текущей версией. Пропуски — признак настройки промптов, а не только модели: эти виды дефектов размечены и в фикстурах.
