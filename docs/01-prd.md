# 01. PRD — ReqCheck, агент ревью требований

Рабочее имя продукта: **ReqCheck**. Python-пакет: `reqcheck`.

## 1. Проблема

Дефекты в требованиях (двусмысленность, непроверяемость, противоречия, пропуски) обнаруживаются поздно, на разработке или тестировании, где их исправление дороже всего. Ручное ревью долгое, зависит от человека и редко сверяет документ целиком (например, часть A с дочерней спецификацией API).

## 2. Пользователи

| Роль | Что нужно | Где работает |
|---|---|---|
| Жюри хакатона | Повторить прогон по README и получить тот же по структуре отчёт | CLI |
| Бизнес/системный аналитик | Загрузить документ, получить список дефектов с цитатами и вопросы, которые надо задать автору | Веб-интерфейс |
| QA / тест-лид | Понять, готов ли документ к тест-дизайну, и что именно непроверяемо | Отчёт PDF/MD |
| Инженер интеграции банка | Встроить проверку в Confluence/Jira/GitLab CI, использовать внутренний LLM-шлюз | HTTP API, JSON, Docker |

## 3. Цели и метрики

| Цель | Метрика | Целевое значение |
|---|---|---|
| G1. Находить заложенные дефекты | Доля найденных дефектов из `expected.yaml` на фикстурах (recall) | ≥ 0,70 |
| G2. Не выдумывать дефекты | Ложные срабатывания на «чистой» фикстуре | ≤ 2 находки уровня «нарушение» |
| G3. Каждая находка проверяема | Доля находок в отчёте с цитатой, найденной в документе кодом | 100 % |
| G4. Лучше наивного подхода | Recall агента − recall baseline «один промпт» | > 0 при не большем числе ложных |
| G5. Укладываться в бюджет | Стоимость одного прогона документа до 10 страниц на модели по умолчанию | ≤ $0,05 |
| G6. Быстро | Время прогона документа до 10 страниц без кэша | ≤ 3 мин |

## 4. Объём

### MVP (день хакатона)
- Вход: PDF (с текстовым слоем), Markdown, TXT.
- Выход: формат входа (PDF → PDF, MD/TXT → MD) + `report.json`.
- Все разделы отчёта из п. 6 ТЗ + раздел «Вопросы к автору документа».
- CLI одной командой; веб-интерфейс на одном экране; HTTP API.
- OpenRouter с выбором модели; кэш; оценка стоимости; предохранитель бюджета.
- Фикстуры, eval, baseline, юнит-тесты.

### P1 (если останется время, в этом порядке)
1. **Цитата в исходном документе** (см. FR-25…FR-27):
   - исходный PDF с пометками: каждая подтверждённая цитата выделена, в комментарии к выделению — находка и предложение;
   - фрагмент оригинала в UI: при раскрытии находки — страница PDF (или абзац Markdown) с подсвеченной цитатой;
   - кликабельные ссылки «стр. N» в PDF-отчёте, ведущие в исходник с пометками.
- DOCX на входе и выходе.
- OCR сканов (Tesseract `rus`).
- HTML-версия отчёта.
- Docker-образ.

### Вне объёма
- Исправление документа за автора (только предложенные переформулировки в отчёте).
- Авторизация пользователей, многопользовательность, хранение истории.
- Запуск тестов ПО, анализ кода.

## 5. Пользовательские сценарии

- **US-1.** Как участник, я запускаю `python main.py docs/requirements.pdf out/report.pdf` и получаю PDF-отчёт и `out/report.json`.
- **US-2.** Как аналитик, я перетаскиваю файл в окно браузера, выбираю модель, вижу прогресс по этапам и скачиваю отчёт в том же формате.
- **US-3.** Как интегратор, я отправляю файл в `POST /api/v1/checks` и забираю JSON-отчёт по идентификатору.
- **US-4.** Как интегратор банка, я направляю агента на внутренний OpenAI-совместимый шлюз одной переменной `LLM_BASE_URL`.
- **US-5.** Как участник с бюджетом $1–2, я вижу оценку стоимости до прогона, а прогон останавливается, если превышен `--max-cost`.

## 6. Функциональные требования

Формулировки пишем так, как требуем от проверяемых документов: одно требование — одно проверяемое утверждение.

### Вход
- **FR-1.** Агент принимает файл `.pdf`, `.md`, `.markdown`, `.txt` размером до 20 МБ.
- **FR-2.** Для файла другого типа агент завершает работу с кодом выхода 2 и сообщением, в котором перечислены поддерживаемые форматы.
- **FR-3.** Для PDF без текстового слоя агент сообщает, что нужен OCR, и завершает работу с кодом 3 (MVP); в P1 запускает OCR.

### Выделение требований
- **FR-4.** Агент присваивает каждому требованию идентификатор отчёта вида `R-001` в порядке появления в документе.
- **FR-5.** Если у требования есть идентификатор в документе (например, `Ф-2`, `FR-12`, `4.3.1`), агент сохраняет его в поле «ID в документе»; иначе поле содержит «—».
- **FR-6.** Для каждого требования агент сохраняет точную цитату из документа и якорь (раздел, пункт, строка/страница).
- **FR-7.** Агент делит составное утверждение на отдельные требования и помечает исходное как составное (нарушение единичности).
- **FR-8.** Строки таблиц критериев приёмки и параметров API считаются требованиями своего типа (`acceptance`, `api`).

### Проверка
- **FR-9.** Каждое требование оценивается по девяти характеристикам п. 5.2.5 ISO 29148: необходимость, независимость от реализации, однозначность, полнота, единичность, реализуемость, проверяемость, корректность, соответствие. Каждая получает вердикт `ok`, `violation` или `unclear`.
- **FR-10.** Набор оценивается по п. 5.2.6 ISO 29148 и п. 4.3 IEEE 830: полнота, непротиворечивость, отсутствие дублей, единообразие терминов, ранжирование, модифицируемость, трассируемость, реализуемость в целом.
- **FR-11.** Каждая находка содержит: категорию, серьёзность (`blocker`, `major`, `minor`), цитату, якорь, объяснение, предложенную переформулировку.
- **FR-12.** Находка, цитата которой не найдена в документе кодом (порог сходства 90), не попадает в отчёт и сохраняется в `report.json` в `debug.dropped_findings`.
- **FR-13.** Вердикт «можно начинать разработку и тестирование» вычисляет код по порогам из `config/thresholds.yaml`, а не модель.

### Отчёт
- **FR-14.** Отчёт содержит разделы в порядке: паспорт прогона; нарезка требований; проверка каждого требования; проверка набора; сводка; вопросы к автору; итог.
- **FR-15.** Паспорт содержит: имя файла, SHA-256 документа, дату и время прогона (UTC+5), модель, версию агента (`git describe`), число вызовов LLM, токены, стоимость.
- **FR-16.** Раздел «Вопросы к автору» содержит не более 10 вопросов; у каждого 2–4 варианта ответа, область влияния и допущение, которое агент принял бы без ответа.
- **FR-17.** Итог содержит не более 5 первоочередных исправлений, упорядоченных по серьёзности.
- **FR-18.** Формат отчёта определяется расширением пути вывода; если расширение не задано, используется формат входа.

### Модель и стоимость
- **FR-19.** Модель задаётся в порядке приоритета: флаг `--model`, поле в интерфейсе, переменная `LLM_MODEL`.
- **FR-20.** До первого вызова LLM агент выводит оценку числа вызовов, токенов и стоимости в долларах.
- **FR-21.** Если накопленная стоимость прогона превысила `--max-cost` (по умолчанию $0,50), агент прекращает вызовы LLM и выпускает отчёт с пометкой «прогон неполный».
- **FR-22.** Повторный прогон того же документа с той же моделью и промптами не вызывает LLM, если кэш не отключён флагом `--no-cache`.

### Интерфейс
- **FR-23.** Веб-интерфейс состоит из одного экрана: загрузка файла, выбор модели, запуск, прогресс по этапам, сводка, скачивание отчёта.
- **FR-24.** Ключ LLM никогда не передаётся в браузер.

### Цитата в исходном документе (P1)
- **FR-25.** Для PDF-входа агент выпускает копию исходного документа, в которой каждая подтверждённая цитата выделена аннотацией-маркером; текст аннотации: ID находки, серьёзность, объяснение, предложение.
- **FR-26.** В UI раскрытая находка показывает фрагмент оригинала с подсвеченной цитатой: для PDF — изображение страницы (обрезанное до области цитаты с полями), для Markdown — абзац цитаты и по одному соседнему абзацу.
- **FR-27.** Если цитата найдена в PDF частями (перенос строки, ячейка таблицы), подсвечиваются все части; если координаты не найдены (скан без текстового слоя), находка показывается без фрагмента с пометкой «место в оригинале не найдено».

## 7. Нефункциональные требования

- **NFR-1. Воспроизводимость.** Повторный прогон с кэшем даёт побайтно одинаковый `report.json` без поля `run.started_at`.
- **NFR-2. Производительность.** Документ до 10 страниц обрабатывается за 3 минуты или быстрее при отсутствии ошибок 429.
- **NFR-3. Надёжность.** При ответе 429/5xx агент повторяет вызов до 5 раз с экспоненциальной паузой от 2 до 60 с и учитывает `Retry-After`.
- **NFR-4. Безопасность.** Текст документа не пишется в логи уровня INFO и выше; отправляется только в настроенный LLM-эндпоинт.
- **NFR-5. Конфиденциальность.** Веб-интерфейс не загружает ресурсы с внешних доменов (шрифты и скрипты лежат локально).
- **NFR-6. Доступность.** Интерфейс соответствует WCAG 2.1 AA по контрасту и управляется с клавиатуры.
- **NFR-7. Переносимость.** Запуск на macOS и Linux с Python 3.12+.

## 8. Критерии приёмки MVP

| Условие | Действие | Ожидаемый результат |
|---|---|---|
| Чистый клон, ключ в `.env` | Выполнить команды из README | Отчёт создан по указанному пути, код выхода 0 |
| `requirements.md` из ТЗ | Прогон с выводом `.md` | Все 7 разделов, у каждой находки есть цитата и якорь |
| Та же команда повторно | Прогон с кэшем | 0 вызовов LLM, одинаковый JSON |
| PDF-фикстура с дефектами | `eval` | recall ≥ 0,70, отчёт PDF открывается и читается кириллицей |
| Чистая фикстура | `eval` | ≤ 2 нарушений |
| Браузер | Загрузить PDF → «Проверить» | Прогресс по этапам, кнопка скачать PDF |

## 9. Риски продукта

| Риск | Влияние | Мера |
|---|---|---|
| Модель выдумывает нарушения | Потеря доверия жюри | Проверка цитат кодом, вердикт `unclear`, вердикт итога считает код |
| Бюджет кончится до финала | Нет финального отчёта | Кэш, дешёвая модель для разработки, `--max-cost` |
| На месте выдадут PDF-скан | Пустой вход | Явное сообщение (MVP), OCR (P1) |
| Отчёт слишком длинный для чтения | Жюри не дочитает | Сводка и итог наверху в UI; в документе порядок задан ТЗ |
