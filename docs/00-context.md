# 00. Контекст

Снимок на 2026-11-25. Источник ТЗ: https://github.com/BCC-HUB/ai-requirements-validator-task (клон только для чтения: `../ai-requirements-validator-task`, коммит `928c1aa`).

## Зачем этот проект

Хакатон BCC-HUB x MNU FinTech. Нужен ИИ-агент, который делает **статическое ревью готового документа требований** до разработки: выделяет отдельные требования, проверяет каждое и весь набор по ISO/IEC/IEEE 29148:2018 (п. 5.2.5, 5.2.6) и IEEE 830-1998 (п. 4.3), пишет отчёт на русском. Отчёт формирует только агент, ручные отчёты не принимаются.

Сдаём: репозиторий с агентом + отчёт, сгенерированный агентом по выданному документу.

## Проверяемый документ

`docs/requirements.md` в репозитории ТЗ — **Markdown**, не PDF. Это комплект из двух частей в одном файле:
- **Часть A** — «Месячный порог расходов по карте» (мобильный банк): цели, архитектура, UI, BPMN, Ф-1…Ф-4, sequence, НФТ, данные, интеграция, критерии приёмки (таблица), чек-лист ревью (не заполнен), блок согласующих (пустой).
- **Часть B** — REST API сохранения порога: параметры, логика, статусы, примеры ответов.

Наблюдения, влияющие на дизайн агента (не хардкодить, только учитывать класс):
- Слов «должен/должна» почти нет → выделение требований должно опираться на структуру (нумерация `Ф-N`, разделы, строки таблиц, параметры API), а не на модальные глаголы.
- Дефекты заложены намеренно и разнесены между частями A и B → проверка набора обязана работать **через границу частей**.
- Есть шаблонные пустоты («заполняются тестировщиками», пустые чек-листы) → это дефекты полноты/процесса, а не отдельных требований.
- Есть таблицы, валюта `₸`, тиыны/тенге, время по Алматы → нормализация текста и чисел важна для поиска противоречий.

Документ на месте может прийти в другом формате (PDF). Агент не должен зависеть от этого конкретного текста.

## Решения команды (от владельца проекта, 2026-11-25)

| # | Решение |
|---|---|
| D1 | **Формат выхода = формат входа**: PDF → PDF, Markdown → Markdown. Плюс всегда машиночитаемый `report.json` рядом |
| D2 | Якорь без страниц: `Часть A › Функциональные требования › Ф-2` + цитата; для PDF добавляется `стр. N` |
| D3 | Имена переменных окружения — наш выбор, к примеру из ТЗ не привязаны |
| D4 | **Провайдер — OpenRouter** (OpenAI-совместимый API) с выбором модели. Бюджет $1–2, поэтому дешёвые модели для разработки, сильная — для финального прогона. К Gemini доверие низкое, но в списке он остаётся |
| D5 | Нужен **минимальный веб-интерфейс**: белый фон, чёрный текст, синие компоненты, мало элементов, всё работает, аккуратные анимации, единая дизайн-система |
| D6 | Агент должен **легко встраиваться** в системы банка (библиотека, CLI, HTTP API, Docker, JSON-контракт, свой LLM-шлюз) |
| D7 | Остальные неоднозначности решает инженер; решения фиксируются в [08-decisions.md](08-decisions.md) |

## Расхождения пересказа и оригинала (уже учтены)

1. Вход — Markdown, а не только PDF. Поддерживаем оба.
2. Документ — комплект из двух частей.
3. `.env.example` в ТЗ — лишь пример (`GEMINI_*`, устаревшая `gemini-1.5-flash`); мы используем OpenRouter.
4. Веб-интерфейс изначально был вне рамок, теперь добавлен решением D5.

## Ограничения

- Срок: один день хакатона.
- Бюджет LLM: $1–2 на OpenRouter. Нужны кэш, оценка стоимости до прогона, предохранитель по стоимости.
- Отчёт обязан быть воспроизводимым по инструкции другим человеком.
- Никаких секретов в репозитории; `.env`, кэш и отчёты прогонов не коммитятся.
